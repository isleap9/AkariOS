# AkariOS: agent guide

PowerShell 5.1 + WPF app that debloats and optimizes Windows 10 22H2 / 11 for gaming. `src/Akari.ps1` is the entry point (GUI and CLI, presets).

- Vocabulary: [`docs/GLOSSARY.md`](docs/GLOSSARY.md). Use its terms in code, comments and docs (Tweak, Toggle, Choice, Action, Group, Entry, Apply, Revert, Default, State, Preset, Run, Outcome).
- Plan and target architecture: [`docs/PLAN.md`](docs/PLAN.md). Decisions: [`docs/adr/`](docs/adr/).
- Repo root: `README.md`, `LICENSE`, `CREDITS.md`, this file; `src/` = what Akari runs from and the release zip ships (every path below without a folder is under `src/`: `Akari.ps1`, `Core/`, `UI/`, `Tweaks/`, `Presets/`, `OneClick/`, `Assets/`); `tests/` (Pester; fixtures in `tests/Fixtures/`); `build/` (`Bootstrap.ps1`, `Launcher.cs` + `Launcher.manifest` = `AkariOS.exe`, `Icons.ps1` = `src/UI/Icons.xaml`, `AppIcons.ps1` = `src/Assets/Apps/`, dev-only); `docs/`; `.github/`; `graphify-out/` (the graphify knowledge graph, kept in the repo); `app/` (the native app, below).

Two apps share this repo (ADR 0007): **the PowerShell app** (`src/`, everything under "Current layout") and **the native app** (`app/`, C# WPF on .NET 10, no PowerShell engine; plan `docs/plans/2026-10-31-native-app.md`). Both ship in the same `v<version>` release. The native app reads `src/` data as it is, so a change there can break it: see "Native app" below.

## Current layout (transitional)

The port is in progress (M1 Engine, M2a Manual steps, M3 Windows port + Presets and M4 One-click, M5 Import / Export done; plans in `docs/plans/`).

- `Akari.ps1`: `-Resume` branch (a Run in phases goes on after a restart: RunOnce, console only, `Get-AkariRun` → `Start-AkariPhases`, summary at the end), CLI branch (`-List`, `-Apply id,id`, `-Revert id,id`, `-Preset <name|file.json>`, `-RevertPreset <name|file.json>`; all but `-List` need an elevated shell; preset wildcards read what is on the PC; a preset Run goes through `Start-AkariPhases`, so a preset with Phases restarts between them), then elevation (the elevated console stays visible: launch banner, live log), Core and tweak loading, and dot-sourcing `UI/*.ps1`; after the window closes for One-click, the AkariOS preset's Run in the console (`New-AkariPresetRun`, `Start-AkariPhases`).
- `Core/` (dot-sourced function files, no tweak logic):
  - `Log.ps1`: `Write-AkariBanner` (the console banner: the logo in `Assets/ascii.txt` through `Get-AkariBannerArt`, dots white, `+` / `=` dark grey; the old text banner if the file is missing), `Write-Log` (GUI queue, printed to Akari's console window, or straight to the console), `Write-ErrLog` (`%LOCALAPPDATA%\Akari\akari.log`), `Write-AkariProblems <problems> <show>` (the loader's Problems: Warnings to akari.log only, Errors through `<show>` too), `Write-AkariCrash <error> [-Wait]` (`Akari.ps1`'s trap, which covers every branch: akari.log, then a message box when WPF is loaded, else the console; `-Wait` for the RunOnce consoles).
  - `Compat.ps1`: no-op / dialog shims for legacy tweak bodies (`Write-Host`, `Pause`, `Read-Host`, file pickers). Loaded only in the GUI job.
  - `Trusted.ps1`: `Run-Trusted`; `Invoke-AkariRegistryTrusted <rows> <Mode>` (HKLM registry rows written as TrustedInstaller, a few per `Run-Trusted` call; for keys an admin can't change, e.g. Defender's).

  - `Loader.ps1`: `Get-AkariTweaks <TweaksRoot>` → `@{ Tweaks; Groups; Problems; Ported }`, `Import-AkariTweakFile`, `ConvertTo-AkariTweak`. Rules in plan §7. One owner per registry value: `Find-AkariRegistryOwner <tweak> <index>` rejects a Tweak setting a value (or something inside a key row) another one-file Tweak already owns; the rows loaded so far are kept in `New-AkariOwnerIndex` / `Add-AkariRegistryOwner` (lookups, not pairs: the pairwise check took ~18 s). `Requires` must be in `$AkariRequirements`. `Guided = $false`: shown on Optimize › Advanced only (default: Guided too); Section `Tools` (checks, Refresh, drivers, cleanup) is the Catalogue's only. `Get-AkariPorted` reads `Tweaks/Ported.psd1`, `Test-AkariPorted <ported> <all tweaks>` (pure) reports ids that don't exist. Data-list Groups (ADR 0002, `EntryKind` in `$AkariEntryKinds`: `AppxRemove`, `CapabilityRemove`, `FeatureDisable`, `StoreInstall`; each kind = its button, restart flag and Apply / Detect text): Entries `<group-id>/<name>` built by `New-AkariEntry` (named from the data file row, `Get-AkariEntryRow`; `Keep` from the row or the Group's `KeepNames` patterns). `Rows` kinds (AppxRemove, StoreInstall) load every data file row as a Tweak; the other kinds list only what is on the PC, so their Entries exist once the GUI reads them; `Resolve-AkariEntry` builds any Entry from its id (the GUI's job and the CLI use it).
  - `Appx.ps1`: engine side of the Remove tab. `AppxRemove`: `Get-AkariAppxPackages` (the only raw read; tests mock it), `Get-AkariAppxInstalled [<packages>]` (an already-read list, else it reads), `Get-AkariAppxLogos <packages>` (package name → its app list logo file, from each AppxManifest.xml: the Apps tables' icons), `Test-AkariAppxInstalled`, `Remove-AkariAppx` (all users + provisioned copy; refuses the never-list `$AkariAppxNever`). `CapabilityRemove`: `Get-AkariCapabilitiesInstalled`, `Test-AkariCapabilityInstalled`, `Remove-AkariCapability`. `FeatureDisable`: `Get-AkariFeaturesEnabled`, `Test-AkariFeatureEnabled`, `Disable-AkariFeature`. The DISM cmdlets are only called through these.

In those blocks a cmdlet error fails the tweak (`-ErrorAction Stop` by default), but a native tool's stderr (`reg.exe`, `powercfg`) is only logged: never set `$ErrorActionPreference = 'Stop'` around native calls (5.1 aborts on their stderr). A Core wrapper with a `[Parameter(...)]` param is an advanced function and takes that `-ErrorAction Stop` too: it sets `$ErrorActionPreference = 'Continue'` before its native call (`Invoke-AkariRegExe`, `Invoke-AkariPowerCfg`).

- Release: `AkariOS-Native.exe` (self-contained single file, win-x64), attached to the same release as the zip by `.github/workflows/release.yml`; `.github/workflows/native.yml` builds and tests on push. Portable; it updates itself from About.
- User data: presets shared in `%LOCALAPPDATA%\Akari\presets`; the rest in `%LOCALAPPDATA%\AkariOS.Native` and `%ProgramData%\AkariOS.Native` (log, state, settings, `run.json`, the exe copy a Run in phases resumes from, files written out for tools).

When changing `src/`: a new field or syntax in a Tweak file or `.psd1` list needs `PsData` / the native Loader in the same change; a new script-block Tweak shows up in `app/parity.txt` (refresh it); MainWindow.xaml's `Window.Resources` is read by the native app too (keep it one block, presentation and x namespaces); a new brush goes in both themes as before (both apps read them). The native app never reads Legacy (`Tweaks/*.ps1`, `Ported.psd1`).

## Rules

1. One tweak per file. If a file passes ~150 lines, split it. Data-list Groups (same-shape Entries) may be one data file (ADR 0002).
2. Every Toggle and Choice has a Revert to the stock Windows Default (ADR 0001). A Tweak is an Action only when no Default exists; the file says why in one line.
3. No tweak logic in `Core/`. Core = helpers, loader, runner only.
4. The GUI never hard-codes tweaks; it builds from the loader output.
5. Open only the tweak file(s) being changed; don't read the whole `Tweaks/` tree or a bundled `Akari.ps1`.
6. HKCU changes must target the real logged-in user hive, not the elevated/SYSTEM one.
7. Tweak script blocks must not be interactive: no `Pause`, `Read-Host`, `Clear-Host`.
8. Credit upstream sources in `CREDITS.md` when porting a tweak.
9. Never copy code from Winhance (PolyForm Shield). Ideas and layout only.
10. Update this file in the same change whenever the layout or a Core API changes.
11. `_ref/` is reference only: read a file there only when the task names it; never scan it whole, never commit or bundle it.
12. Never launch the GUI or run the CLI on the developer's real machine, in tests or by hand. Tests use fixture tweaks, `HKCU:\Software\AkariTest\<guid>` and `TestDrive:`; CLI tests use `-List` or fake ids. The user does all real testing on a VM — never on the developer's machine. System-changing native commands (`bcdedit`, `shutdown`, …) are called only through a PowerShell function (e.g. `Invoke-AkariBcdEdit`) and tests mock that function, asserting the mock was hit: Pester 3 does not reliably mock a native command (a `Mock cmd` let the real `bcdedit` run once). The native app follows the same rule: each tool or system API through one interface, faked in tests.
13. The native app shares the PowerShell app's vocabulary, Tweak ids and rules 1-12. No code from Winhance or AkariOS-Companion.
