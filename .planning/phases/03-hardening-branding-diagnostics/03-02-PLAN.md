<objective>
Give the user a restore point they created themselves, before anything destructive
happens, and tell them plainly that they have one.

The engine already creates a restore point — but at `steptwo.ps1:1217`, at the very end
of Stage 3, after the removals. That is not a safety net for the install; it is a
snapshot of an already-modified system. SAFE-01 asks for a restore point **before Stage
1** with **explicit confirmation**, and neither exists anywhere in the codebase. Both
are new work.

Purpose: make the destructive confirmation gate mean something. Today SAFE-02 asks the
user to type `AKARIOS` and then removes Defender, UAC, VBS and the GPU drivers with no
way back. After this plan there is somewhere to go back to, and the user is told it
exists.
Output: `New-AkariOSRestorePoint` behind a seam, a truthful confirmation card, an
acknowledgement path for failure, and a recorded restore point identity that Wave 1's
summary reads back.
</objective>

**T-03-17 — `New-AkariOSRestorePoint` in `functions/private/RestorePoint.ps1`.**
Parameters: `[string]$Description = "AkariOS pre-install safety point"`,
`[string]$RestorePointType = "MODIFY_SETTINGS"`,
`[string]$StatePath = $script:AkariOSStateDefaultPath`,
`[scriptblock]$RestorePointInvoker`.

The `-RestorePointInvoker` default is the ONLY place `Checkpoint-Computer` appears:
`{ param($desc, $type) Checkpoint-Computer -Description $desc -RestorePointType $type -ErrorAction Stop }`.
Follow the `Invoke-AkariOSEngine` pattern exactly, INCLUDING the null-invoker fallback —
a `$null` invoker must not reach `& $null` and return a fictitious success (the Phase 2
bug class). Use `-ErrorAction Stop` in the default, not `SilentlyContinue`: the engine's
`-ErrorAction SilentlyContinue` is precisely why nobody would ever learn that its restore
point failed, and repeating it here would make D-19's truthful-failure requirement
unimplementable.

Return an object, always: `Created` (bool), `Description`, `SequenceNumber`, `CreatedAt`,
`Error` (the exception message, or `$null`), `AlreadyExists` (bool, from the
frequency-limit path).

**T-03-18 — Frequency-limit handling (a real failure mode, not a hypothetical).**
Windows rate-limits System Restore to one point per 24 hours by default, so a user who
just installed something, or who re-runs AkariOS, gets `0x80070002`-class errors from
`Checkpoint-Computer` even though nothing is wrong. Handle it as a DISTINCT outcome:
first read the newest existing point through an injectable `-RestorePointReader`
(default `Get-ComputerRestorePoint`, wrapped in try/catch), and when creation fails with
a frequency-limit-shaped error AND a point created within the last 24 hours exists,
return `Created = $true`, `AlreadyExists = $true`, and the EXISTING point's identity —
which is the truth, because the user does have a recent restore point. When creation
fails for any other reason, return `Created = $false` with the reason (D-19). The
frequency-limit detection must be a pure helper `Test-AkariOSRestorePointRateLimited
-ErrorRecord -Existing -Now` so the harness can drive every branch without a machine
that has rate limits.

**T-03-19 — `Set-AkariOSRestorePointRecord`, writing the identity through the `Object`
set.** Adds a `RestorePoint` note property
(`Description`, `SequenceNumber`, `CreatedAt`, `CreatedByAkariOS = $true`) to the state
object with `Add-Member -Force`, then `Set-AkariOSState -Path $StatePath -State $obj`.
NEVER `Set-AkariOSState -Fields` — T-02-26 proved the `Fields` set rebuilds the object
field by field and silently drops any property it does not enumerate, which is exactly
how a recorded stage failure evaporated on the first progress tick. On a failure, do NOT
write a `RestorePoint` block at all, so a stale success from a previous attempt is never
mistaken for this one's.

**T-03-20 — The confirmation card.** `Show-AkariOSRestoreResult -Result

exactly. On `Created`, show `RestoreResultTitle` = "Restore point created", and
`RestoreResultDetail` naming the description, the sequence number and the timestamp —
the user must be able to identify the point later, not just be told "done". On
`AlreadyExists`, say plainly that an existing point from the last 24 hours is being used
and name it. On failure, show `RestoreResultTitle` = "Restore point NOT created", the
reason, and a warning that the install will be harder to undo. Controls live in a new
`xaml/panels/05-Restore.xaml` fragment with a `PanelRestore` root, plus `NavRestore` in
`MainWindow.xaml` and registration in `main.ps1`'s `$panels` / `$navMap` / `$navNames`
(all three).

**T-03-21 — Wire it into `Invoke-BtnInstall`, in the right order.** After
`Invoke-PreFlightChecks` passes and BEFORE `Show-ConfirmationGate` (D-19: the user
creates the point, THEN consents — not after, which would be consent for a change they
have not yet seen the safety net for):

1. `Get-AkariOSRestorePointStatus -RestorePointReader` — if a point created within the
   last 24 hours already exists, do not create another (rate limit); show the card as
   `AlreadyExists` and continue to the gate.
2. Otherwise `New-AkariOSRestorePoint`.
3. On `Created = $false`, show the failure card and require explicit acknowledgement
   before proceeding. Use `-AcknowledgeInvoker` so the harness can drive it. The default
   is a typed-token dialog modeled on `Show-ConfirmationGate` — reuse its window,
   its `[hashtable]`-outcome pattern and its explicit close, but a DIFFERENT token from
   `AKARIOS` so the two consents cannot be confused for each other. Record which path
   was taken in the log at INFO, because a later reader needs to know whether the user
   ever had a restore point.
4. Only then call `Show-ConfirmationGate` and, on success, `Start-AkariOSInstall`.

Do NOT edit `Show-ConfirmationGate` itself. Add the new step around it.

|----------|-------------|
| AkariOS -> System Restore | `Checkpoint-Computer` asks the VSS/RM service to create a snapshot of the whole system; it is slow, it consumes disk, and it can fail for reasons the user cannot see |
