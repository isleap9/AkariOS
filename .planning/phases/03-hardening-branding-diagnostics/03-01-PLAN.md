<objective>
Close the one gap Phase 2 left open and make the install's result visible.

Two things, in this order. First, the mechanism: after `steptwo.ps1` calls
`shutdown -r -t 00` the GUI must come back by itself. Today it does not, because no
relaunch mechanism exists anywhere in the codebase — and the obvious one (a RunOnce
entry) is destroyed before it can fire, because the read-only engine wipes the RunOnce
keys three times at `steptwo.ps1:324-333`. Second, the payoff: the screen the user sees
when it comes back is DIAG-04's "what changed" summary, listing what was removed,
disabled and applied, with links to the restore point and the log.

This is Wave 1 because everything else in Phase 3 is downstream of it. SAFE-01's
restore-point link needs a screen to appear on. BRND-01 runs from this relaunched
session, because the engine's Stage 3 overwrites any wallpaper written earlier. And
until this plan lands, no one has ever seen anything AkariOS draws.

Purpose: the install currently ends in silence. This plan makes it end in an answer.
Output: a scheduled-task relaunch created behind a seam, a completion check that reuses
the existing resume predicate, a summary panel, and a self-cleanup that leaves nothing
behind.

   likely to be got wrong by intuition, so state the reason explicitly: a task running

   be created on a desktop the user cannot see. The completion screen would still be
   invisible — the exact symptom this plan exists to fix, reached by the obvious-looking
   route. The task therefore targets the interactive user with `/IT` and `/RL HIGHEST`,
   and falls back to `/RU SYSTEM` **only** when the interactive account name cannot be
   resolved, logging a WARN so the degradation is never silent. Confirm the fallback is
   acceptable, or require that a failed resolution abort the task creation instead.

3. **The relaunch target is a staged copy under `%ProgramData%\AkariOS\` (D-15).** The
   user may have run `akarios.ps1` from Downloads, from a temp path, or from a file
   they have since deleted. The task's command line must point at something that will
   still be there. Confirm staging a copy is preferred over pointing at the running
   script's own path.

4. **`Start-AkariOSInstall` remains the single install entry point, and the relaunch
   task creation hangs off Stage 3 inside `Invoke-AkariOSStage`, not off the button

## Threat Model

### Trust Boundaries

| Boundary | Description |
|----------|-------------|
| AkariOS -> Task Scheduler | AkariOS creates a task that runs at every logon until it deletes itself; a malformed or hijacked task is arbitrary code at sign-in |
| AkariOS -> staged script file | The relaunch task points at a copy of the running script under ProgramData, which is writable by admin and by anything that gets admin |
| Summary text -> WPF | Catalog text and log excerpts are rendered into `TextBlock`s; log content is attacker-influenceable only by whoever can write install.log |
| Summary buttons -> shell | Two actions launch external processes (`SystemPropertiesProtection.exe`, `explorer.exe`) — both by fixed name, never built from user input |

<verification>
Every check in this plan is static or seam-injected. Nothing here executes
`schtasks.exe`, writes a registry key, creates a real scheduled task, invokes
`bcdedit`, reboots, downloads, executes an engine stage, or touches
`C:\ProgramData\AkariOS`. The one place a real side effect is permitted is
`Copy-AkariOSRelaunchScript` copying bytes **inside a `$env:TEMP` scratch directory**,
which is neither destructive nor system state.

Phase gate after this plan: `Test-Relaunch.ps1` and `Test-Summary.ps1` both exit 0 with
their PASSED lines; the four mutations were each proven to turn a harness RED and back
GREEN with the results recorded in `03-01-SUMMARY.md`; the four engine MD5s match
upstream; `WinSux-main/` is untouched; and the compiled `akarios.ps1` parses with zero
errors, carries all ten new control names in its `$inputXML` here-string as plain `Name=`
attributes, and defines all nine new symbols exactly once.

What this gate does NOT prove — and must not be read as proving — is that the GUI
actually comes back after Stage 3's reboot, or that the window is visible rather than on
session 0. Those are the two headline behaviours and both are VM-only. They are items 1
and 2 in the VM list above and belong to Phase 4.
</verification>
