<objective>
Make the machine look like AkariOS, in AkariOS code, without touching the engine.

BRND-01 asks for four things: OEM information, a logo, wallpaper/lockscreen, and system
branding. WinSux already sets a black wallpaper and a black lockscreen at
`steptwo.ps1:763-780` — which is precisely the constraint that shapes this plan. Anything
AkariOS wrote before that point would be overwritten, so branding must run from the
post-install relaunched session that Wave 1 built. That is the whole reason BRND-01 is
Wave 4 and not Wave 1.

Purpose: the user asked for "rebrand to AkariOS" to mean literally that, not just an app
name (PROJECT.md, Key Decisions). What ships is a machine that reports itself as AkariOS
in `msinfo32`, shows the AkariOS logo in the OEM panel, and boots to an AkariOS
wallpaper and lockscreen.
Output: a branding layer behind three seams, an idempotent apply path, a per-step result
report, and a panel that shows what was applied and what was not.
</objective>

**T-03-38 — `Get-AkariOSBrandImagePath -Directory` and
`New-AkariOSLogoBitmap -ImageWriter`.** `Get-AkariOSBrandImagePath` derives
`%ProgramData%\AkariOS\<LogoFileName>` from a parameter defaulting to the house ProgramData
directory — never a literal path, for the same reason `Diagnostics.ps1` carries no
`ProgramData` literal (asserted by its own harness).

`New-AkariOSLogoBitmap -ImageWriter` renders a 120x120 24-bit BMP via
`System.Drawing`: a solid AkariOS-accent background with the word "AKARI" drawn in the
segment display font at a legible size. **120x120 BMP is not a style choice** —
`OEMInformation\Logo` is documented as a BMP of about that size and anything else renders
wrong or not at all. The default `-ImageWriter` does the real `Bitmap` / `Graphics` /
`Save` work; it writes to a temp name and moves it into place, so an interrupted render
never leaves a truncated BMP that OEM Information will happily display. Return the path.

The real renderer is NEVER invoked by a harness with a real output path: on the authoring
machine, exercise it against a `$env:TEMP` scratch path only. That IS a real
`System.Drawing` render and a real file write, both harmless and both worth running —
a bitmap path that is only ever tested through a stub proves nothing about whether
`Save` even works.

**T-03-39 — `Set-AkariOSOemInformation -RegistryWriter`.** Writes the six OEM strings
plus `Logo` (the path from T-03-38) under
`HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\OEMInformation`. The `-RegistryWriter`
default receives a `(Path, Name, Type, Value)` quadruple and performs
`reg.exe add "<Path>" /v "<Name>" /t <Type> /d "<Value>" /f` — the same
string-built-command-through-a-seam shape `Set-AkariOSRunOnceEntry` uses, so the
`bcdedit`-outside-a-seam assertion idiom has a direct precedent. Skip `SupportPhone` and
`SupportHours` when empty rather than writing empty strings; an empty support field
renders as a blank line in the OEM panel and looks like a bug.

Return a per-value result array, each `{ Name, Written, Reason }`. A single failed value
must not abandon the rest — partial success reported as partial success, never as one
boolean.

**T-03-40 — `Set-AkariOSWallpaper -RegistryWriter -WallpaperInvoker`.** AkariOS's own
image: generate a wallpaper sized to the primary monitor
(`[System.Windows.Forms.SystemInformation]::PrimaryMonitorSize`, the same source the
engine uses), write it to `%ProgramData%\AkariOS\akarios-wallpaper.jpg`, then:

- `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\PersonalizationCSP` ->
  `LockScreenImagePath` (REG_SZ) and `LockScreenImageStatus` (REG_DWORD `1`) — the same
  two values `steptwo.ps1:775-776` sets, which is precisely why branding must run AFTER
  the engine (D-25). Setting these is what makes the lockscreen show the AkariOS image
  rather than the engine's black one.
- `HKCU\Control Panel\Desktop` -> `Wallpaper` (REG_SZ) — the same value
  `steptwo.ps1:779` sets, under the SAME hive. Overwriting HKCU from an elevated process
  writes the elevated user's hive, which after the engine's changes may not be the hive
  the interactive session reads; call this out explicitly in the code comment and log
  line, and note it as a VM verification item. This is a real, known WPF/PowerShell
  footgun and pretending otherwise would be dishonest.

The `-WallpaperInvoker` default issues
`rundll32.exe user32.dll, UpdatePerUserSystemParameters` — reachable only through the
seam, exactly as `Clear-BcdSafebootValue` does for `bcdedit`. Return per-value results
like T-03-39.

**T-03-41 — `Invoke-AkariOSBranding -RegistryWriter -ImageWriter -WallpaperInvoker
[-StatePath] [-LogPath]`.** The orchestrator. Order: render the logo -> apply OEM strings

too, rather than shipping a summary that silently omits the most visible change of the

is worse than no record.
